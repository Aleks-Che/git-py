# Справочник по проекту для разработчиков и ИИ-агентов

Карта текущей рабочей копии, сверенная с кодом **2026-09-05**.
Документ помогает найти точку изменения и связанные проверки; архитектурные
требования остаются в [AGENTS.md](../AGENTS.md), [ARCHITECTURE.md](ARCHITECTURE.md)
и [DEVELOPMENT_RULES.md](DEVELOPMENT_RULES.md).

## Начало новой сессии

1. Прочитайте [AGENTS.md](../AGENTS.md) и запрос пользователя. Выполните
   `git status --short` и просмотрите уже имеющийся diff: рабочая копия может
   содержать незавершённые изменения. Сохраняйте их при выполнении своей задачи.
2. Для структурных решений прочитайте архитектуру, правила разработки,
   [план реализации](IMPLEMENTATION_PLAN.md) и [план тестирования](TEST_PLAN.md).
3. Найдите нужные модули по карте ниже. Сверьте реализацию с ближайшими тестами;
   комментарии об этапах и датированные отчёты могут описывать прежнее поведение.
4. Проверьте интерпретатор и установку `.[dev]`. Команды установки для обеих
   платформ приведены в [README](../README.md).
5. Выберите проверки по затронутому поведению. При начале или завершении этапа
   обновляйте его чек-лист в `IMPLEMENTATION_PLAN.md`; отдельно описывайте
   фактические результаты проверки, ограничения и оставшиеся задачи.

Документация проекта ведётся на русском языке. В отчёте указывайте,
какие команды действительно запускались; результаты старого ревью не являются
результатом проверки текущей рабочей копии.

## Стек, импорты и сборка

- Python **3.10+**, PySide6 **≥ 6.5**, pygit2 **≥ 1.12**; версии и настройки
  инструментов определены в [pyproject.toml](../pyproject.toml).
- `src` — имя верхнеуровневого Python-пакета. Импортируйте, например,
  `from src.core.models import FileChange`. Не смешивайте с `from core...`:
  разные пути могут создавать разные экземпляры одного Python-модуля.
- Запуск из корня: `python -m src.main`. В `pyproject.toml` нет console script;
  сборка использует setuptools и **явный список пакетов**. При добавлении
  подпакета обновляйте `[tool.setuptools].packages`.
- В Windows [run.cmd](../run.cmd) запускает `python -m src.main` из папки
  проекта через `python` из `PATH`, передаёт аргументы и сохраняет код завершения.
  При ошибке выполняет `pause`, чтобы сообщение было видно при двойном щелчке.
- Dev-зависимости: pytest, pytest-qt, pytest-asyncio, Ruff. В pytest заданы
  `testpaths = ["tests"]`, `pythonpath = ["src"]`, `qt_api = "pyside6"`.
  Editable-установка и запуск из корня сохраняют доступность пакета `src`.
- Ruff: длина строки 100, целевой Python 3.10; набор правил — в `pyproject.toml`.
- Git CLI необходим для чтения статуса, rebase, SSH clone/fetch/push и вспомогательных операций.
  Обёртки находятся в `core/operations.py`. GitPython сейчас не используется
  и не входит в зависимости.
- [CI](../.github/workflows/ci.yml) работает на Ubuntu с Python 3.10/3.11/3.12,
  устанавливает `libgit2-dev`, запускает Ruff и pytest с offscreen Qt.
  Это не матрица проверки всех настольных ОС.

## Связи слоёв и поток данных

```text
Виджет → метод MainViewModel → GitCommand → core.operations → RepositoryManager / Git
                               ↓
                     CommandProcessor: история
                               ↓
               обновление ViewModel → сигналы → виджеты
```

`MainViewModel` владеет текущим `RepositoryManager`, `CommandProcessor` и
ViewModel графа, коммита и веток. `MainWindow` связывает их с панелями и вкладками.
Смена репозитория сбрасывает относящиеся к нему состояние, кэши и историю команд.

| Сценарий | Где искать |
| --- | --- |
| Открытие и обновление репозитория | `MainViewModel.open_repository`, `set_repository`, `load_repository_data`, `refresh_state` |
| Статус и коммит | `CommitPanelViewModel` → `MainViewModel.commit_changes` → `CommitCommand` |
| Граф | `RepositoryManager.get_all_history` → `GraphViewModel` → `graph_v2.build_graph` → `graph_to_dicts` → `GraphTableWidget` |
| Выбор коммита и diff | `selection_changed`, `request_commit_detail`, `request_commit_file_diff` → `RightPanel` / `DiffViewWidget` |
| Ветки и tracking | `RepositoryManager.branches` → `BranchPanelViewModel` → `LeftPanel`; операции — в `MainViewModel` |
| Конфликт | `MergeConflictError` → `conflict_state_changed` → `ConflictPanel` / `ConflictResolutionDialog` |
| Undo/Redo | `MainViewModel.undo/redo` → `CommandProcessor`; обновление UI через `stack_changed` |

## Правила изменения поведения

- `core/` не импортирует PySide6. Модели и раскладка графа независимы от виджетов.
  Исключения pygit2 оборачиваются в доменные типы из `exceptions.py`.
- ViewModel использует Qt-сигналы, но не знает конкретных виджетов. Публичные
  действия называются глаголами; ошибки передаются через `error_occurred(str)`.
- Виджеты отображают состояние и передают действия. Новые изменяющие Git-операции
  оформляйте как `GitCommand` с регистрацией в `CommandProcessor`.
  Существующие исключения описаны в `DEVELOPMENT_RULES.md`; не расширяйте их
  автоматически на новые действия.
- У команды должны быть определены результат и границы отмены.
  `PushCommand` и `FetchCommand` имеют `is_noop=True` для истории Undo:
  выполняют Git-операцию, но не дают пользователю фиктивный откат.
  Ошибка Undo/Redo сохраняет команду для повторной попытки и передаётся через сигнал.
- При переписывании истории сохраняйте проверки HEAD/ref, индекса,
  tracked/untracked/ignored-файлов и дерева назначения. Undo не должен стирать
  изменения, появившиеся после исходной команды. Примеры — в `commands.py`
  и `operations.ensure_safe_tree_update`.
- Merge из меню и drag-and-drop передаёт `no_ff=True`; программный
  `merge_branch` сохраняет возможность fast-forward. Проверяйте оба сценария.
  При fast-forward с `no_ff=True` индекс и рабочие файлы обновляются через SAFE
  checkout **до** создания merge-коммита. После перемещения HEAD старые версии
  иначе воспринимаются как staged-правки и остаются в рабочей папке.
  Регрессии: `tests/core/test_merge_no_ff.py` (изменение/удаление/добавление,
  другая целевая ветка, отказ при пересечении с локальными правками,
  сохранение посторонних staged/unstaged-изменений).
- Пути, горячие клавиши и параметры интерфейса проходят через `utils/config.py`;
  сохраняйте неизвестные ключи при записи настроек.

### Редактирование файла из diff

`DiffViewWidget` показывает Edit для текстового просмотра Staged/Unstaged.
Состояние хранит `FileEditorViewModel` внутри `CommitPanelViewModel`, файловое
чтение и защищённая запись находятся в `core/file_edit.py`. Чтение в рабочем UI
фоновое, с отбрасыванием устаревших ответов через `LatestWorker`.

Редактор всегда открывает полный файл из рабочей папки, в том числе при выборе
Staged: Save не меняет индекс. Save активна только при отличии от последней
сохранённой версии; `hotkeys.save_file` по умолчанию задаёт Ctrl+S, действующий
при фокусе внутри редактора. Save оставляет режим редактирования открытым.
Cancel отбрасывает только несохранённый текст и возвращает diff. Смена файла,
стороны Staged/Unstaged, режима просмотра, коммита, репозитория и закрытие окна
автоматически сохраняют черновик; ошибка записи сохраняет черновик и блокирует
переход. Фоновое обновление статуса не заменяет редактируемый текст.

Во время редактирования меню и toolbar Undo/Redo связаны с локальной историей
текстового документа. После выхода они снова управляют `CommandProcessor`;
каждое сохранение представлено `SaveFileCommand`. Save/Undo/Redo сравнивают
содержимое на диске с ожидаемой версией и отказываются перезаписывать внешние
изменения. Запись заменяет файл атомарно, сохраняя BOM, кодировку и окончания
неизменённых строк. Поддерживаются UTF-8 и UTF-16/32 с BOM; бинарные, удалённые,
невалидные текстовые файлы и символические ссылки не открываются для правки.
`file_editor_max_bytes` (по умолчанию 2 МиБ) ограничивает размер полного документа,
чтобы редактор не сохранял обрезанный предпросмотр большого файла.
Регрессии: `tests/core/test_file_edit.py`, `tests/viewmodels/test_file_editor.py`,
`tests/ui/test_file_editor.py`.

### Индекс и подпись обычного коммита

`core.operations.commit_changes()` перечитывает индекс с диска через
`index.read(force=True)` перед созданием дерева. `CommitCommand` передаёт
`stage_all=False`: в коммит входят только staged-версии, а последующие изменения
рабочих файлов остаются unstaged. `CommitPanelViewModel.stage_file()` также
перечитывает индекс перед изменением одного пути, чтобы сохранить остальные записи
после внешних коммитов и staging. Фоновое обновление списков через отдельный
`RepositoryManager` само по себе не обновляет индекс основного подключения.

Генерация сообщения читает отдельный снимок HEAD → index и не меняет индекс.
В Settings → AI → Edit prompts есть две вкладки: сообщение коммита и разрешение
конфликтов. На первой сохранены язык сообщения и пресеты, а галочка
«Добавлять название ветки» раскрывает независимые варианты summary/description.
`ai.include_branch_name` управляет добавлением, `ai.branch_in_summary` и
`ai.branch_in_description` задают поля. По умолчанию добавление выключено;
при включении выбран summary. После генерации приложение дописывает `[имя-ветки]`
в конец summary и/или отдельным абзацем в конец description. Префикс Conventional
Commits сохраняется, имя не переводится; при detached HEAD метка не добавляется.

На второй вкладке `ai.conflict_language` выбирает готовую инструкцию на русском,
английском, немецком, испанском, французском, китайском или японском языке.
Текст остаётся редактируемым; кнопка «Промпт по умолчанию» восстанавливает
шаблон текущего языка. При переключении языков внутри диалога сохраняются
локальные черновики; в конфиг записываются выбранный язык и текущий текст
`ai.conflict_prompt`. Он подхватывается при следующем открытии AI-разрешения.
Язык инструкции не связан с языком сообщения коммита. Cancel редактора или
внешнего Settings отбрасывает изменения; старые пользовательские промпты сохраняются.

Нельзя использовать успешную генерацию как подтверждение свежести кэша подключения,
которое затем создаёт коммит. Регрессии с внешним коммитом, фоновым обновлением,
Stage All и ручным/сгенерированным сообщением: `tests/ui/test_ai_workflow.py`;
сохранение частичного staging и обработка ошибки чтения: `tests/core/test_operations.py`.

Для обычного коммита без явно переданного `committer` используется та же подпись,
что и для `author`, включая время и часовой пояс. Поэтому настроенный пользователь
не заменяется на `git-py <git-py@localhost>` в поле коммиттера. Явный отдельный
коммиттер сохраняется; история ранее созданных коммитов не переписывается.

### SSH-ключи и настройки подключения

- Генерация по умолчанию использует `~/.ssh/git-py-ed25519`; путь задаёт
  `utils.config.default_ssh_key_path()`. Каталог создаётся при необходимости.
  Если `.ssh` занят файлом или недоступен, диалог сообщает ошибку и сохраняет
  выбранный путь; автоматического переноса в `.ssh-py` или temp нет.
- Генерация из Settings сразу сохраняет только пути ключей, даже при последующем
  Cancel. Генерация из Clone передаёт `key_generated` через MainWindow в
  `MainViewModel.configure_ssh_key()`. Остальные изменения Settings требуют OK.
- `MainViewModel` перечитывает ключ из своего `config_path` перед каждой сетевой
  операцией. Путь передаётся через Push/Pull/Fetch/FetchAndCheckoutCommand в Core;
  clone также получает его явно. Уже сохранённые пользовательские пути, включая
  `.ssh-py`, продолжают работать, если приватный ключ существует.
- `core.operations._ssh_environment()` сохраняет окружение процесса, передаёт
  приватный ключ через `GIT_SSH_COMMAND` с безопасным shell quoting и включает
  `IdentitiesOnly=yes`. Несуществующий выбранный ключ вызывает `AuthError`.
  Без выбранного ключа остаётся системный выбор SSH. Для push учитывается `push_url`.
- Регрессии: `tests/core/test_ssh_auth.py`, `tests/viewmodels/test_ssh_settings.py`,
  `tests/ui/test_ssh_setup.py` и `tests/ui/test_clone_dialog.py`. В тестах генерируемые
  ключи изолированы от домашнего каталога пользователя, внешняя сеть не используется.

### Фоновые операции

Дифф выбранного файла WIP (включая staged и Full document) при
`async_enabled=True` загружается через `utils/latest_worker.py::LatestWorker`.
Пустой результат показывает пояснение «No diff to display» с подсказкой про
нормализацию LF/CRLF: файл может оставаться Modified при отсутствии текстового
патча. Это placeholder, который не попадает в копируемый diff и действия staging;
при следующей загрузке или закрытии просмотра он сбрасывается.
Этот же исполнитель обслуживает диффы коммитов/stash в `MainViewModel`:
для каждого источника максимум два активных чтения и один заменяемый ожидающий
запрос. Повторный запрос уже загружающегося ключа не запускает второй воркер.
Смена выбора/репозитория и закрытие окна инвалидируют результаты и ошибки;
потоки не прерываются принудительно и GUI не ждёт их завершения.

`core/file_diff.py` просматривает `Diff.deltas` и создаёт патч только для
совпавшего пути через `diff[index]`. Перебор `for patch in diff` для одного
файла использовать нельзя: он вычисляет также патчи остальных файлов.
Чтение WIP и фильтрация staged-строк выполняются в Core на собственном
`RepositoryManager` воркера. Синхронный `build_diff_text` сохранён для Copy Diff.

`MainWindow` отображает только `diff_pair_ready`, чтобы не рисовать дифф
повторно по legacy-сигналу `diff_ready`. `DiffViewWidget` показывает анимацию
после 150 мс ожидания и блокирует действия над строками до результата.
Лимиты отображения: 20 000 строк, 1 000 000 символов, 4 000 символов в одной
строке. Пропуски обозначаются явно и не доступны для построчного staging;
полный исходный текст сохраняется. Регрессии: `test_file_diff.py`,
`test_file_diff_async.py`, `test_diff_loading.py` и `test_right_panel.py`.

`MainWindow` создаёт `MainViewModel(async_enabled=True)`. Значение по умолчанию
у самого ViewModel — `False`, чтобы простые тесты могли работать синхронно.

- Сетевые и долгие операции выполняются через `AsyncWorker`; фоновые мутации
  используют `_mutation_pool` с `maxThreadCount=1`. Чтение деталей и истории
  использует отдельные задачи на глобальном пуле.
- `_run_async` открывает собственный `RepositoryManager` внутри воркера.
  Не передавайте один изменяемый pygit2 handle нескольким потокам.
- Воркер выполняет команду; `CommandProcessor.record_success/record_failure`
  меняют историю в GUI-потоке после получения результата. Это относится
  также к асинхронным Undo/Redo.
- Сохраняйте `is_busy`/`busy_changed`, поколение `_async_generation` для
  отбрасывания устаревших результатов и ссылки `_active_workers` до завершения.
  Проверяйте повторный запуск, смену репозитория и закрытие окна.
- `AsyncWorker.failed` передаёт объект исключения: сначала разбирается его тип
  и контекст конфликта, затем формируется сообщение для UI.

### Конфликты и внешние изменения

`ConflictResolutionDialog` показывает две выровненные версии: слева целевую,
справа вливаемую, с ветками, SHA и заголовками коммитов. Третье поле снизу —
результат. `core/conflict_resolution.py` сравнивает обе стороны с общим предком:
независимые изменения попадают в результат сразу; конфликтующие строки выбирает
пользователь. Совпадающий контекст не дублируется. Внутри каждого конфликта
строки добавляются в порядке кликов; разные конфликты сохраняют места в файле.
Чекбокс добавляет ещё не выбранные строки стороны, второй чекбокс дополняет
результат. Минус возвращает выбранную строку наверх. Пустая сторона выбирается
чекбоксом; бинарные файлы сохраняют выбор одной байтовой версии целиком.

Состояние выбора и черновик принадлежат `ConflictEditorViewModel`. Виджет
`ConflictTextWidget` повторно использует gutter и цвета обычного diff и выделяет
также изменённые символы. Результат редактируется вручную; его неизменённые
перенесённые строки сохраняют связь с источником для удаления через минус.
Размеры диалога и двух splitter хранятся в `conflict_editor_layout` через config.

«Решить с помощью AI» открывает общую инструкцию (`ai.conflict_prompt`) и
пользовательский контекст (`ai.conflict_context`), сохраняемые для следующих
файлов. Используются текущие URL, ключ, модель и timeout. Локального лимита
входного запроса нет: допустимый размер определяет API провайдера;
`ai.max_diff_chars` применяется только к генерации сообщения коммита.
AI получает все конфликтующие участки открытого файла, base/ours/theirs, diff
и по восемь строк соседнего контекста; неизменённая часть собирается локально.
Ответ обязан содержать ровно запрошенные ID участков и текст каждого решения;
неполный JSON, повторные/неизвестные ID и маркеры конфликта отклоняются.
Ошибка HTTP 413 сообщает об отказе провайдера из-за размера запроса.
Запрос работает через LatestWorker, с индикацией, блокировкой
повторного запуска и игнорированием позднего ответа после отмены/закрытия.
Ответ заполняет черновик; запись происходит по «Сохранить решение».

`ResolveConflictCommand` проходит через CommandProcessor, а запись находится
в Core. Исходный снимок проверяет репозиторий, HEAD, операцию, стадии индекса
и содержимое рабочего файла; при внешнем изменении черновик остаётся открыт.
Для существующего файла запись атомарная; сохраняются выбранная кодировка,
доминирующие LF/CRLF и отсутствие завершающего перевода строки. Отдельная
промежуточная запись не добавляется в Undo: её откат принадлежит операции
merge/rebase; CompleteMergeCommand сохраняет прежний цикл Undo/Redo.
Rename-конфликты, символические ссылки и submodule требуют внешнего инструмента.

В Windows libgit2 удерживает открытые pack-файлы даже после чтения истории.
`RepositoryManager.release_handles()` вызывает
[`pygit2.Repository.free()`](https://www.pygit2.org/repository.html#pygit2.Repository.free):
освобождает файловые дескрипторы, сохраняя возможность следующих чтений.
`MainViewModel` вызывает его на GUI-потоке через `aboutToBlock` диспетчера Qt,
когда обработка событий завершена, а также при смене репозитория и закрытии окна.
Каждый фоновый менеджер освобождается через `close()` в `finally`, включая
клонирование и чтение staged-снимка. Освобождать менеджер из другого потока во
время операции нельзя; фоновые задачи должны владеть отдельным менеджером.
Наличие ссылки на raw repo или traceback не должно откладывать освобождение
до сборки мусора. Git lock-файлы при этом не удаляются.

Оболочка встроенного терминала запускается только при вводе первой команды:
простое открытие репозитория не удерживает его каталог как cwd дочернего процесса.
После запуска оболочка сохраняет интерактивную сессию, в том числе при скрытии
панели; перед переименованием всей папки такую сессию можно завершить командой
`exit` или закрыть вкладку репозитория. Скрытие панели не прерывает команды.
Регрессии с реальным Windows rename и внешним `git repack`:
`tests/core/test_repository_handles.py`, `tests/viewmodels/test_repository_handles.py`,
`tests/ui/test_terminal_widget.py`.

При `async_enabled=True` `MainViewModel` проверяет файловую систему
и индекс через отдельный `RepositoryManager` в фоне, с паузой по умолчанию
в одну секунду после завершения предыдущего опроса. Это локальный мониторинг,
не связанный с auto-fetch или фокусом окна. Он только читает состояние: правки
после staging появляются в Unstaged, сохраняя ранее staged-версию того же файла.
Повторное сохранение выбранного файла обновляет diff даже без изменения Git-флагов.
Неизменившиеся списки не перерисовываются; история для WIP пересчитывается только
при изменении числа изменённых файлов. Сообщение коммита и Undo-стек сохраняются.

Одновременно работает максимум один запрос мониторинга. Результаты, полученные
до staging, другой операции, смены репозитория или закрытия окна, отбрасываются.
Мониторинг останавливается при закрытии окна. Запрос полного обновления по фокусу,
поступивший во время занятой операции, выполняется после её завершения.
Проверки: `tests/core/test_worktree_status.py`, `tests/viewmodels/test_worktree_refresh.py`,
`tests/ui/test_worktree_refresh.py` и `tests/ui/test_main_window.py`.

Чтение статуса для панелей и мониторинга проходит через
`RepositoryManager.get_raw_status()` → `core/status.py`: отдельный процесс
`git --no-optional-locks status --porcelain=v1 -z --untracked-files=all --no-renames`.
Прямой `pygit2.Repository.status()` может удерживать GIL на всём сканировании:
перенос такого вызова в QRunnable сам по себе не гарантирует отзывчивость GUI.
CLI не обновляет индекс, на Windows запускается без консольного окна; ошибки
и timeout передаются как `GitError`, без тихого возврата к блокирующему сканированию.
Пути git-dir/work-tree заданы явно, унаследованные переменные выбора репозитория
удалены из окружения дочернего процесса. NUL-разделители сохраняют необычные имена;
флаги staged/unstaged/conflict совместимы с текущими ViewModel. Отключение rename
соответствует прежнему статусу pygit2 (удалённый и добавленный пути отдельно).
Игнорируемые Windows junction-каталоги учитываются по правилам Git CLI.

Фоновая загрузка репозитория и пересчёт WIP передают уже прочитанный `raw_status`
в `GraphViewModel._compute_graph()`: один опрос активной папки на обновление.
Оценка размера merge использует `diff.deltas`, не перебор патчей `for patch in diff`.
Регрессии: `tests/core/test_status.py`, `tests/viewmodels/test_status_performance.py`.
Замеры и воспроизведение: [PERFORMANCE_WORKTREES.md](PERFORMANCE_WORKTREES.md),
`python -m tools.profile_worktree_status <repo> [<linked-worktree>] --repeat 3`.

`core.worktree_status.read_other_worktree_changes()` читает собственные HEAD
и индекс каждой зарегистрированной рабочей папки через отдельный менеджер.
Из связанного worktree также видна основная рабочая папка; текущая исключается.
Чистые, игнорируемые и отсутствующие папки не создают узлов. Staged и unstaged
версии одного файла считаются один раз. Сканирование не меняет индекс или refs.

Для каждого изменённого соседнего worktree `GraphViewModel` создаёт WIP-узел
со стабильным ID по пути и родителем из его HEAD. Узел использует обычные
DAG-связи и стиль WIP; detached HEAD включается в историю без создания ветки.
Правая панель показывает ветку, путь, число файлов и `Open worktree in new tab`.
Кнопка и контекстное меню передают запрос через `MainViewModel` в существующую
модель вкладок: новая вкладка активируется, открытая повторно используется.
Редактирование/commit/stash доступны после перехода в соответствующую вкладку.
Мониторинг сравнивает путь, ветку, HEAD и счётчик соседних worktree; при изменении
перестраивает граф, при исчезновении выбранного WIP закрывает его панель.
Регрессии: `tests/{core,viewmodels,ui}/test_other_worktrees.py`.

Checkout из графа (включая popup) и списка локальных веток вызывает
`MainViewModel.request_checkout_branch()`. Локальная ветка определяется по refs,
поэтому слеши в `agents-ide/run/...` не превращают её в remote. Core-функция
`find_branch_worktree()` перечитывает HEAD зарегистрированных соседних папок,
включая чистые worktree и основную папку при переходе из связанной; индексы
и статус для поиска не сканируются. Если ветка уже открыта в другой папке,
`open_worktree_requested` активирует её вкладку или создаёт новую через
`RepoTabViewModel.add_tab()`. HEAD, индекс и рабочие файлы обеих папок сохраняются.
Если worktree нет, выполняется обычный `CheckoutCommand` с Undo. Busy и ошибка
сохранения редактора блокируют переход. Внутренние последовательности команд
сохраняют `checkout_branch()`, чтобы не менять репозиторий посреди операции.
Регрессии: `tests/{ui,viewmodels}/test_branch_worktree_checkout.py`.

Ветки, открытые в соседних worktree, отмечены контурным деревом слева от имени
на графе и в `BranchStackPopup`. Значок относится к локальной ветке независимо
от наличия WIP; текущая ветка и remote-копия на том же SHA не получают эту метку.
`read_branch_worktrees()` читает только HEAD соседних папок. `GraphViewModel`
передаёт путь через `branch_refs[].worktree_path`; полный снимок `branch_worktrees`
в первой строке графа нужен фоновому монитору, включая ветки за лимитом истории.
Смена ветки/переход в detached HEAD снаружи обновляет метки без повторных обходов
истории на неизменившихся тиках. Размер дерева берётся из `branch_icon_size`
и учитывается при расчёте прокрутки; всплывающая подсказка строки popup показывает
путь. Регрессии: `tests/ui/test_worktree_branch_icon.py` и
`tests/viewmodels/test_other_worktrees.py`.

Крестик вкладки передаёт координаты клика в системе `QTabBar`, чтобы закрывалась
именно нажатая вкладка. При перетаскивании `RepoTabViewModel.move_tab()` обновляет
порядок путей, сохраняя активный репозиторий; виджет не пересоздаёт кнопки во время
drag. Этот порядок используется при закрытии и сохранении сессии. Регрессии:
`tests/ui/test_repo_tab_close.py`, `tests/viewmodels/test_repo_tabs_viewmodel.py`.

Состояние конфликта принадлежит ViewModel. `ConflictPanel` вызывает Resolve,
Continue и Abort через сигналы, подключённые в `MainWindow`.
Первый конфликтующий файл выбирается автоматически, поэтому Resolve открывает
диалог и при нескольких файлах без предварительного клика по списку. Обновление
списка сохраняет выбор по пути; если файл исчез, выбирается первый оставшийся.
`continue_operation()` перечитывает индекс, чтобы увидеть в том числе внешний
`git add`. `complete_merge_after_conflict()` использует `CompleteMergeCommand`;
продолжение rebase — `ContinueRebaseCommand` и `RebaseContinueResult`.
Кнопка Continue вызывает `request_continue_operation()`: при фоновом обновлении
репозитория клик запоминается и выполняется один раз после успешной загрузки
и завершения воркера. Повторные клики объединяются. Ошибка загрузки, смена
репозитория или изменение Git-операции отменяют ожидающий запрос. Для выполняемой
Git-команды сохраняется обычная блокировка. Загрузка держит `busy` до
`lifespan_finished`, без вложенного `processEvents()` в обработчике результата.
`set_repository()` восстанавливает незавершённую merge/rebase-операцию с диска.

Проверяйте полный цикл: конфликт → разрешение → Continue → Undo → Redo,
а также Abort, повторное открытие и разрешение через внешний Git.
Контекст фонового конфликта должен сохранять источник и целевую ветку.

### Ошибка очистки после создания stash

`stash_push()` и `stash_push_staged()` различают создание архива и очистку
рабочей папки: новый `refs/stash` может уже существовать, когда удаление файла
или каталога завершилось ошибкой. `StashSaveError.saved_oid` содержит SHA нового
архива; существовавший до попытки stash не выдаётся за результат операции.
Если проверить ссылку после ошибки не удалось, сохранение не подтверждается.

Блокировка распознаётся по тексту sharing/locking violation: pygit2 не передаёт
числовой WinError, поэтому используются системные описания Windows 32/33 и
английские/русские варианты. Обычный Access denied не называется блокировкой.
Уведомление указывает путь, сохранённый SHA при наличии и объясняет, почему часть
изменений осталась. Имя удерживающего процесса не определяется; автоматической
повторной очистки нет. Исходная диагностика остаётся в журнале.

Все три VM-входа (общий, staged и один файл) обновляют граф, stash и файлы после
`StashSaveError`, отклоняя устаревший снимок фонового мониторинга. Ошибка идёт
через `error_occurred(str)`; неуспешная команда не добавляется в Undo.
Проверки: `tests/core/test_stash_failures.py`, `tests/viewmodels/test_stash_failures.py`,
`tests/ui/test_stash_errors.py`; Windows-проверки удерживают настоящие handles
только во временных репозиториях и закрывают их в `finally`.

## Где менять и что проверять

### Создание тегов на графе

Меню коммита и чипа локальной/удалённой ветки содержит `Create tag here…`.
`GraphTableWidget.create_tag_requested(sha)` передаёт SHA строки в
`MainWindow._on_create_tag_here()`: диалог запрашивает имя и вызывает
`MainViewModel.create_tag()`. Создаётся локальный lightweight-тег без checkout;
после успеха обновляются граф и левая панель. Отмена, пустое имя или смена
репозитория во время диалога не создают тег. В меню WIP/stash этого пункта нет.

`CreateTagCommand` проходит через `CommandProcessor`. Core `create_tag()`
возвращает OID созданной ссылки: commit для lightweight или объект annotated-тега.
Undo передаёт его в `delete_tag(expected_target=..., missing_ok=True)`, чтобы
сохранить тег, заменённый внешней операцией; ошибки остаются в истории для повтора.
Регрессии: `tests/core/test_tags.py`, `tests/viewmodels/test_tag_commands.py`,
`tests/ui/test_graph_tags.py`.

### Просмотр изображений

Клик по изображению в правой панели открывает `ImageViewWidget` в той же центральной
области, где показывается текстовый diff. `utils/image_preview.py` распознаёт расширения
форматов Qt (включая PNG, JPEG, GIF, BMP, WebP, SVG, ICO, TIFF) и декодирует содержимое
через `QImageReader`. Анимированные файлы показываются первым кадром.
Чтение и декодирование выполняет `MainViewModel.request_file_image()` в фоне; устаревшие
результаты после смены файла, стороны или репозитория отбрасываются.

`RepositoryManager.read_file_content()` возвращает исходные байты: unstaged — рабочая
папка, staged — индекс, коммит/stash — выбранное дерево. Для удаления используется
предыдущая сторона (индекс, HEAD или первый родитель соответственно), а просмотрщик
показывает пометку `before deletion`. Чтение не меняет Git. Виджет получает готовый
`QImage`, отображает размеры и версию, поддерживает колесо мыши и перемещение
перетаскиванием. Повреждённый или неподдерживаемый файл показывает сообщение об ошибке.

Просмотр сценариев без запуска: `python -m pytest --collect-only -q`.
В Bash: `QT_QPA_PLATFORM=offscreen python -m pytest`.
На Windows для Git CLI выбирайте короткий уникальный `--basetemp` вне репозитория:

### Фикстуры и изоляция

В [tests/conftest.py](../tests/conftest.py) определены:

- `tmp_git_repo` — путь к пустому временному репозиторию с веткой `main`;
- `committed_repo` — `RepositoryManager` с двумя коммитами и файлом `hello.txt`;
- `make_commit` — фабрика коммитов для нужной топологии истории.

Фикстуры используют `tmp_path` и pygit2; `core.autocrlf=False` изолирует
байтовые проверки от глобальной настройки разработчика. Сетевые сценарии
строятся на локальном bare-репозитории или моках. Не используйте рабочий
репозиторий пользователя как тестовый.

Qt-тестам нужен event loop даже без видимых окон. Для ожидания сигналов
и фоновых результатов используйте средства `qtbot`. Тесты конфигурации передают
`MainWindow(config_path=tmp_path / "config.json")`; `config_path=None` отключает
сохранение окна. Чтение конфигурации в отдельных ViewModel изолируйте отдельно.
На Windows `conftest.py` задаёт `QT_QPA_FONTDIR`, если он ещё не задан:
геометрические и пиксельные тесты зависят от доступных шрифтов.

## Конфигурация и диагностика

Источник значений — `_DEFAULT_CONFIG` в [utils/config.py](../src/utils/config.py).
Путь к JSON вычисляет `default_config_path()` через Qt `QStandardPaths`, поэтому
не зашивайте абсолютный путь пользователя в код или тест.

`load_config()` проверяет известные типы, диапазоны чисел, режим diff, пути
вкладок и вложенные AI/hotkey-поля; неверные значения заменяются defaults,
неизвестные ключи сохраняются. Невалидный UTF-8 обрабатывается как повреждённый
JSON. Размеры, передаваемые в Qt, ограничены диапазоном его целых чисел.
`save_config()` записывает уникальный временный файл рядом с целевым и атомарно
заменяет JSON; параллельные записи больше не используют один `.tmp`.
Это не блокировка нескольких экземпляров приложения: итог полного сохранения
по-прежнему определяется последней успешной записью.

`MainViewModel` загружает начальные настройки из своего `config_path` и явно
передаёт лимиты графу и `CommandProcessor`. Аргументы конструктора для auto-fetch
и порога merge имеют приоритет над JSON; `None` означает значение из конфигурации.
Неположительный интервал отключает auto-fetch. Автор, SSH, таймаут push, AI и
лимит копии Discard перечитываются из того же файла перед соответствующим
действием. У команды Discard лимит фиксируется при создании, включая будущий Redo.

Untracked-файл больше `discard_file_max_backup_bytes` остаётся на диске:
Discard сообщает `GitError` и не добавляется в Undo. Для файла в пределах лимита
работает Undo/Redo; Undo не перезаписывает файл, созданный позже по тому же пути.
Отказ чтения копии также не удаляет исходный файл. Лимит 0 позволяет копировать
только пустые файлы. Это ограничение копии в памяти, а не разрешение удалять без Undo.

Ширины колонок графа запоминаются для фактически открытого репозитория при
`repository_changed` и восстанавливаются для новой вкладки. Сохранение на выходе
объединяет посещённые вкладки с последним JSON на диске; старые варианты записи
пути поддерживаются, новые ключи нормализуются. Если запись при закрытии не
удалась, Cancel оставляет окно и терминал открытыми для повторной попытки,
Discard закрывает без сохранения. Auto-fetch останавливается при закрытии окна.
Регрессии: `tests/utils/test_config.py`, `tests/viewmodels/test_settings_audit.py`,
`tests/ui/test_settings_audit.py`.

## Что легко перепутать

- **Активный граф:** раскладка — `core/graph_v2.py`, отображение —
  `ui/widgets/graph_panel.py::GraphTableWidget`. `core/graph.py` больше нет;
  `graph_widget.py::GraphWidget` оставлен для совместимости. Имя теста
  `test_graph_widget.py` не означает, что он проверяет только старый виджет.
- **Цвет истории и меток:** плашки веток и popup получают цвет по имени.
  В Core имя продолжающейся ветки передаётся по первому родителю независимо
  от колонок графа, включая merge: метка новой/отстающей ветки на старом
  tip не перехватывает цвет обычной линейной истории. При схождении `main/master`
  имеют приоритет над `dev/develop`, затем идут остальные ветки; внутри группы
  локальные refs предпочтительнее remote. HEAD не задаёт приоритет цвета,
  stash/WIP не передают владение историей. Вторые родители merge сохраняют
  отдельные цвета. Первая именованная родительская ветка после merge также
  сохраняет свой цвет, даже если до неё есть коммиты без меток.
  Git не хранит ветку создания коммита, поэтому это правило отображения по
  видимой топологии, а не восстановление исторического авторства ветки.
  Регрессии: `tests/{core,ui}/test_branch_color_continuity.py`.
  Сквозная последовательность команд и переоткрытие:
  `tests/viewmodels/test_branch_color_workflow.py`, кейс TC-GRAPH-COLOR-01
  в `TEST_PLAN.md`.
  Общая история `main` под ответвлением `dev`, включая no-ff merge, и пиксели
  синей вертикали/зелёного ответвления: TC-GRAPH-COLOR-02 в `TEST_PLAN.md`.
- **WIP и stash:** WIP создаёт `graph_v2.build_graph`; `GraphViewModel` передаёт
  число изменений и HEAD, а stash вставляет в историю как `CommitInfo`.
  При чистой рабочей папке верхний stash естественно занимает колонку своего
  основания. Если одновременно есть WIP и stash от HEAD, колонка WIP резервируется
  до прохода по истории; все соединения stash строятся обычным алгоритмом DAG.
  Переносить только значок после раскладки нельзя: так теряются промежуточные
  участки линий. Регрессии: `test_stash_connections_span_intervening_branch_commits`
  в `tests/core/test_graph_v2.py` и `test_stash_graph_regression.py` в
  `tests/viewmodels/` и `tests/ui/`.
  WIP остаётся в колонке HEAD при `HORIZONTAL_PIPE`: пересечение уже содержит
  вертикальное продолжение и хранит его цвет отдельно от горизонтали. Верхний
  `BRANCH_LEFT/RIGHT` дополняется вертикалью вверх через `TEE_LEFT/RIGHT`.
  Сложный двухцветный relay-bend не упрощается: его дополнительный выход вправо
  требует сохранения обхода.
  Обычный `HORIZONTAL` по-прежнему требует обхода; свободная колонка проверяется
  во всех строках до HEAD включительно, а пересекаемые `PIPE` сохраняются как
  `HORIZONTAL_PIPE`. Регрессии: `tests/{core,viewmodels,ui}/test_wip_graph_regression.py`,
  кейс TC-GRAPH-WIP-02 в `TEST_PLAN.md`.
  Старые записи плана описывают другую схему.
- **Remote-дубликаты:** в левой панели совпадения имени недостаточно для
  скрытия remote-ветки; учитываются tip и tracking. Проверяйте diverged upstream
  и ahead/behind, а поведение меток на графе — отдельно.
- **Reset-to-remote:** старые `ARCHITECTURE.md` и `DEVELOPMENT_RULES.md`
  описывают обход `CommandProcessor`. В текущем коде путь идёт через
  `FetchAndCheckoutCommand(force=True)` и последовательный исполнитель.
  Undo восстанавливает ссылки, но не явно отброшенные изменения рабочей директории.
  Не воспроизводите старый обход при добавлении новых операций.
- **Светлая тема:** `_LIGHT_THEME_PLACEHOLDER` не зарегистрирован как рабочая
  тема; запуск применяет dark. Наличие ключа `theme` не означает готовность
  переключателя, светлой темы или импорта/экспорта настроек.
- **Статус этапов:** чек-лист плана помечает этапы 0–8 и 10 завершёнными,
  этап 9 — в работе. Старые сводки `8 / 11`, `9 / 11` и числа тестов
  не согласованы между собой. Settings для автора/SSH уже существует.
- **Отчёты ревью:** [ревью](REVIEW_2026-09-05.md),
  [повторная проверка](REVIEW_2026-09-05_VERIFICATION.md),
  [корневой VERIFICATION.md](../VERIFICATION.md) и `updates/` фиксируют
  определённый момент. Исправления после проверки описаны в конце
  `IMPLEMENTATION_PLAN.md` и проверяются регрессионными тестами.
- **Производительность:** 5000 коммитов и раскладка < 1 секунды — цель из
  `TEST_PLAN.md`, а не гарантия измерения на любой машине. Указывайте топологию,
  размер входа и фактическое время при изменении алгоритма графа.

При изменении структуры, зависимостей, команд запуска или важных контрактов
обновляйте этот справочник и соответствующий проектный документ в той же задаче.
