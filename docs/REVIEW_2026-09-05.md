## Замечания

### 1. [P1] Undo изменения сообщения коммита удаляет незакоммиченные правки

[src/viewmodels/commands.py:914](C:/work/git/my-repos/git-py/src/viewmodels/commands.py:914)

Редактирование сообщения HEAD сохраняет index/worktree, но `EditCommitMessageCommand.undo()` выполняет `reset(..., mode="hard")`. Сценарий: изменить tracked-файл без коммита → изменить сообщение HEAD → Undo. Правки файла исчезают. В воспроизведении `valuable uncommitted work` заменяется содержимым коммита. Снимок этих правок команда не сохраняет.

Исправление: для reword HEAD откатывать только ref, проверяя ожидаемый текущий OID. Для остальных вариантов Undo определить, какие данные операция должна восстанавливать, и сохранять index/worktree либо безопасно отказывать при несовместимых внешних изменениях. Проверить аналогичные hard-reset/force-checkout в Undo merge, pull, rebase и squash. Семантика режимов подтверждается [документацией git reset](https://git-scm.com/docs/git-reset).

Воспроизведение: `reword_undo_loses_worktree`.

### 2. [P1] Drop последнего коммита также удаляет текущие правки

[src/core/operations.py:1061](C:/work/git/my-repos/git-py/src/core/operations.py:1061), [src/ui/main_window.py:963](C:/work/git/my-repos/git-py/src/ui/main_window.py:963)

Ветка `sha == HEAD` сразу выполняет hard reset на родителя. Проверки dirty worktree/index нет; UI предупреждает только о переписывании опубликованной истории. При удалении неопубликованного tip пропадают и изменения, сделанные после коммита. Undo хранит прежний HEAD, поэтому содержимое, которого в коммите не было, не восстановит.

Исправление: проверять состояние до изменения ref; сохранять пользовательские правки либо отклонять Drop с понятным сообщением. Удаление коммита и удаление текущих правок должны быть отдельными явно обозначенными действиями.

Воспроизведение: `drop_tip_loses_worktree`.

### 3. [P1] Squash включает посторонние staged-изменения

[src/core/operations.py:1449](C:/work/git/my-repos/git-py/src/core/operations.py:1449)

Для диапазона, заканчивающегося HEAD, используется soft reset + `commit_changes(stage_all=False)`. Источник дерева нового коммита — текущий index. Если до squash подготовить `unrelated.txt`, этот файл попадёт в результат, хотя его нет ни в одном выбранном коммите.

Исправление: строить новый коммит из дерева верхнего выбранного коммита, сохраняя пользовательский index отдельно, либо до операции требовать чистый index. Изменения refs должны происходить после успешной подготовки результата.

Воспроизведение: `squash_includes_unrelated_staged_file`.

### 4. [P1] Разрешение merge в другую ветку сдвигает постороннюю ветку

[src/core/operations.py:626](C:/work/git/my-repos/git-py/src/core/operations.py:626), [src/core/operations.py:883](C:/work/git/my-repos/git-py/src/core/operations.py:883)

Если из `dev` выполнить merge `feature` в `main`, при конфликте core возвращает символический HEAD на `dev`, оставляя index от слияния в `main`. Затем `complete_merge()` создаёт коммит через `HEAD` и дополнительно передвигает target-ref. В воспроизведении и `dev`, и `main` начинают указывать на результат merge, хотя пользователь изменял только `main`. Если исходные tips различаются, чтение первого родителя через текущий HEAD также использует неверную ветку.

Исправление: держать checkout на target до завершения/abort либо хранить полный контекст операции и создавать коммит с явно сохранёнными родителями и целевым ref. Проверять все затронутые refs, а не только HEAD.

Воспроизведение: `resolve_merge_moves_unrelated_current_branch`.

### 7. [P1] Успешный трёхсторонний merge оставляет MERGE_HEAD

### 11. [P2] Reword/squash молча не работают при длинных сокращениях SHA

[src/core/operations.py:1164](C:/work/git/my-repos/git-py/src/core/operations.py:1164), [src/core/operations.py:1489](C:/work/git/my-repos/git-py/src/core/operations.py:1489)

Скрипты todo сравнивают первые семь символов сохранённого SHA с `parts[1]` через `short.startswith(parts[1])`. При `core.abbrev=12` условие никогда не выполняется. Воспроизведён reword среднего коммита: функция возвращает успех, сообщение остаётся прежним. Такой же способ сравнения используется для squash. Кроме того, reword возвращает CommitInfo старого OID после успешного переписывания.

Исправление: сравнивать полный сохранённый SHA с сокращением Git либо разрешать todo OID в полный. Проверять фактический результат, возвращать новый OID; покрыть `core.abbrev=12` и SHA, для которых семи символов недостаточно. При reword через нелинейную историю отдельно определить сохранение merge-коммитов: обычный rebase их не сохраняет без соответствующего режима ([git rebase](https://git-scm.com/docs/git-rebase)).

Воспроизведение: `reword_abbrev_12_noop`.
