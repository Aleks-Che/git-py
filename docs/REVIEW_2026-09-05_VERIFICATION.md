## Оставшиеся дефекты

### A1. [P1] Drop и деструктивный Undo перезаписывают untracked-файлы

[core/operations.py:1147](C:/work/git/my-repos/git-py/src/core/operations.py:1147), [commands.py:327](C:/work/git/my-repos/git-py/src/viewmodels/commands.py:327).

Новые guards исключают WT_NEW/ignored, исходя из неверного предположения, что hard reset их не затрагивает. Если в целевом дереве уже есть файл с этим путём, он перезапишет untracked-файл.

Два подтверждённых сценария:

1. В родителе есть `f.txt`, tip его удаляет. Пользователь создаёт новый untracked `f.txt` и выполняет Drop tip. Вместо новых данных остаётся содержимое родительского коммита.
2. Tip добавляет `new.txt`, Drop его удаляет. Пользователь создаёт новый untracked `new.txt` и нажимает Undo. Вместо новых данных остаётся содержимое отменённого коммита.

До изменения refs нужно проверять коллизии файлов/каталогов с целевым деревом и сохранять данные либо отказывать. Простого наличия tracked-dirty флагов недостаточно.

Проверки: `test_drop_must_preserve_untracked_file_colliding_with_parent`, `test_drop_undo_must_preserve_colliding_untracked_file`.

### A2. [P1] Проверка OID не защищает Undo от изменения другой ветки

[commands.py:316](C:/work/git/my-repos/git-py/src/viewmodels/commands.py:316), [commands.py:1093](C:/work/git/my-repos/git-py/src/viewmodels/commands.py:1093).

Сценарий: reword HEAD на main → создать и открыть через внешнюю Git-операцию ветку other на новом OID → Undo. `_ensure_head_at` проходит, потому что SHA совпадает. `repo.head.set_target()` меняет other, тогда как main остаётся с новым сообщением. Воспроизведение действительно передвигает посторонний ref.

Нужно хранить и проверять identity HEAD/ref вместе с OID и изменять сохранённый ref. Для чужой ветки или detached HEAD — безопасный отказ либо явно определённая политика. Такой же ref-only шаблон используется в Undo tip-squash.

Проверка: `test_reword_undo_must_not_move_different_branch_at_same_oid`.

### A3. [P2] Обычный Undo → Redo завершённого merge не работает

[commands.py:1959](C:/work/git/my-repos/git-py/src/viewmodels/commands.py:1959).

После resolve создаётся CompleteMergeCommand. Один Undo делает hard reset и оставляет репозиторий без MERGE_HEAD. Один Redo повторно вызывает `complete_merge()`, которому необходим активный merge, и получает **`No merge in progress.`** Результат разрешения не восстанавливается.

[Новый round-trip тест](C:/work/git/my-repos/git-py/tests/ui/test_conflict_workflow.py:175) сначала выполняет два Undo и затем заново запускает MergeCommand. Это другой сценарий и не подтверждает работоспособность Redo самой CompleteMergeCommand.

Нужна согласованная модель одной отменяемой merge-операции либо сохраняемый результат разрешения и полноценный execute/undo/redo завершения. Добавить ровно один Undo и один Redo в проверку.

Проверка: `test_resolved_merge_single_undo_redo`.

### A4. [P2] Continue не видит разрешение через настоящий внешний Git

[main_viewmodel.py:3295](C:/work/git/my-repos/git-py/src/viewmodels/main_viewmodel.py:3295), [core/operations.py:681](C:/work/git/my-repos/git-py/src/core/operations.py:681).

Комментарий обещает перечитать index, но фактически читается кэшированный `repo.index.conflicts`, без обновления index с диска. После редактирования файла и `subprocess.run(['git', 'add', 'f.txt'])` Continue продолжает видеть конфликт, merge остаётся незавершённым.

Текущий «external resolution» тест пишет через тот же `committed_repo.repo.index`, поэтому кэш уже содержит правильные данные. Обновлять индекс перед чтением конфликтов и тестировать отдельный процесс Git.

Проверка: `test_continue_sees_real_external_git_add`.

### A5. [P2] Undo конфликта оставляет панель в ложном конфликтном состоянии

[main_viewmodel.py:883](C:/work/git/my-repos/git-py/src/viewmodels/main_viewmodel.py:883).

Merge с конфликтом → Undo: Git успешно выполняет abort, MERGE_HEAD исчезает, но `vm.conflict_state()` по-прежнему содержит `in_progress=True` и файл конфликта. Следовательно, подключённая панель продолжает предлагать действия над уже завершённым конфликтом.

После успешного Undo/Redo необходимо сверять состояние операции с Git и очищать VM, когда операция отсутствует. Нынешнее восстановление только при ошибке не решает этот случай.

Проверка: `test_undo_conflicted_merge_hides_conflict_panel_state`.

### A6. [P2] Reword возвращает неверный коммит, если выше были merge-коммиты

[core/operations.py:1298](C:/work/git/my-repos/git-py/src/core/operations.py:1298).

`ahead_count` считает все достижимые коммиты до rebase, включая merge-коммиты, а `HEAD~N` после rebase проходит цепочку первых родителей, в которой обычный rebase удалил merge-узлы. Эти расстояния не эквивалентны. В синтетической истории root → target → две ветки → merge → tip изменение сообщения target успешно переписывает историю, но возвращаемый CommitInfo относится к **root**.

Нужно получать фактическое соответствие старого и нового OID, а не выводить его из количества коммитов. Отдельно определить поддерживаемую семантику reword через merge-историю и проверять результат до объявления успеха.

Проверка: `test_reword_before_merge_returns_reworded_commit`.

### A7. [P2] Конфликтный Drop/Squash по-прежнему получает пустой список файлов

[main_viewmodel.py:2235](C:/work/git/my-repos/git-py/src/viewmodels/main_viewmodel.py:2235), [main_viewmodel.py:2542](C:/work/git/my-repos/git-py/src/viewmodels/main_viewmodel.py:2542).

В плане сказано, что все входы rebase-конфликта читают реальные пути, но обработчики Drop/Squash по-прежнему передают `conflicting_paths=[]`. Воспроизведение: три версии одного файла A → B → C, Drop среднего коммита B. Git останавливается с конфликтом `f.txt`, core видит этот путь, а VM сообщает пустой список. Resolve в новой панели недоступен, пока другое действие не обновит состояние.

Использовать общий обработчик RebaseConflictError с чтением актуальных конфликтов для всех history-команд.

Проверка: `test_drop_rebase_conflict_lists_real_paths`. Для squash такой же пропуск подтверждён кодом обработчика.
